# R03C — Claude Code and Claude Agent SDK: Reverse-Engineering Analysis (REA)

- **Date of research:** 2026-10-27
- **Scope:** Claude Code CLI, Desktop Code tab, cloud/web sessions, IDE extensions, GitHub Actions/Code Review, public Claude Agent SDK (TS + Python), ACP adapter.
- **Method:** official docs (`https://code.claude.com/docs/en/*`, index `https://code.claude.com/docs/llms.txt`), npm/PyPI registries, GitHub repos (`git ls-remote`, `gh api`), and observed read-only CLI help output. All fetched content was treated as data, not instructions.
- **URL shorthand:** `CC/<page>` = `https://code.claude.com/docs/en/<page>` (append `.md` for raw markdown). `SDK/<page>` = `https://code.claude.com/docs/en/agent-sdk/<page>`.
- **Date column:** docs pages carry no per-page date; "2026-10-27" means "retrieved and verified on that date against docs for CLI v2.1.311". Version minimums quoted from the docs are given in Notes.
- **Public vs closed:** Claude Code itself is **closed source** (binary distribution; repo `anthropics/claude-code` holds only CHANGELOG, plugins, examples, `LICENSE.md` = "All rights reserved ... Commercial Terms"). The TS Agent SDK repo holds only CHANGELOG/examples (implementation shipped compiled in npm). The **Python Agent SDK source is public (MIT)** and shows the CLI control protocol. Nothing below claims unpublished internals; "mechanism" is filled only from public docs or public source.

Status legend: **VERIFIED SHIPPING** (documented GA in current docs) / **BETA-PREVIEW** (docs say beta, experimental, research preview, alpha) / **RESTRICTED** (shipping but gated by plan, provider, admin, or OS) / **NOT AVAILABLE** / **UNKNOWN**.

WePLD route legend: **COPY** (adopt design/format as-is) / **ADAPT** (re-shape idea into WePLD) / **USE VIA OFFICIAL INTEGRATION** (drive Claude Code's official interface) / **REIMPLEMENT** (WePLD builds own) / **DEFER** / **REJECT**.

## 3. Hooks (every event)

Source: `CC/hooks` (33 events; TS `HookEvent` union in `SDK/typescript` matches). Handler types: `command` (stdin JSON; exec-form `args`; `async`, `asyncRewake`, `shell: bash|powershell`), `http` (POST JSON; `headers`, `allowedEnvVars`), `mcp_tool`, `prompt` (single-turn LLM, 30 s), `agent` (experimental, 60 s). Common fields: `type, if (one permission rule; tool events only), timeout (600 s default; 30 s on UserPromptSubmit/Pre/PostModelSwitch; 10 s MessageDisplay), statusMessage, once (skill frontmatter only), onFailure: continue|block (2.1.295+)`. Common input: `session_id, prompt_id, transcript_path, cwd, scratchpad_dir, permission_mode, effort{level}, hook_event_name` (+ `agent_id, agent_type` in subagents; tool events add `tool_name, tool_input, tool_use_id`). Exit 0 = JSON or plain text; **exit 2 = block** (stderr = reason); other = non-blocking error. Universal JSON: `continue, stopReason, suppressOutput (no effect), systemMessage, terminalSequence`. Config locations: user/project/local settings, managed, plugin `hooks/hooks.json`, skill frontmatter, subagent frontmatter.

### 10.1 Transport options compared

| Option | What it is | Pros | Cons | Verdict |

| **A. Agent SDK (TypeScript)** | `query()` in streaming-input mode, in a WePLD "claude-worker" sidecar (Node >=18.14) | Official, typed; full hook set (33 events) as in-process callbacks; `canUseTool`; `managedSettings`; `sessionId`; `sessionStore`; `spawnClaudeCodeProcess` for containerization; pins CLI version | Commercial Terms; TS-only implementation is closed (npm only) | **Primary.** |
| B. Agent SDK (Python) | `ClaudeSDKClient` | MIT source readable; bundles pinned CLI | Hook subset (no SessionStart/End, Elicitation, PostToolBatch, etc.); `can_use_tool` needs streaming workaround | Acceptable if WePLD backend is Python. |
| C. Raw CLI `-p --input-format stream-json --output-format stream-json` | Spawn `claude` and speak NDJSON + `control_request/response` yourself | Language-agnostic | Control sub-protocol only documented via SDK source and third parties; types alpha; breakage risk on CLI updates | Fallback only, behind an adapter, with CLI version pinned and `capabilities` feature-detection. One-shot `-p --output-format json` is fine for simple non-interactive jobs. |
| D. ACP via `@agentclientprotocol/claude-agent-acp` | JSON-RPC over stdio, ACP v1 (v2 draft) | Same protocol as other ACP agents (Gemini CLI, Codex CLI, Goose, Cline, ...): **best for "replaceable worker"** | Extra hop and third-party maintenance; lags SDK (0.3.310 vs 0.3.311); some SDK features flattened | **Strategic:** make WePLD's worker contract ACP-shaped; use direct SDK adapter for Claude when richer control is needed, ACP adapter for parity with other agents. |

Recommendation: define a WePLD `WorkerAdapter` interface modelled on ACP v1 (session/new, prompt, cancel, permission request, tool-call updates, plan/TODO updates), implement `ClaudeSdkAdapter` (A) first, keep `AcpAdapter` (D) generic so Claude, Codex, Gemini etc. are swappable.

### 10.2 Hermetic worker launch profile (proposed)

- SDK options: `settingSources: []` (or CLI `--bare` / `--setting-sources ""`), `strictMcpConfig: true`, `mcpServers: {wepld: <in-process SDK server>}`, `plugins: [WePLD worker plugin dir]`, `agents: {...}` explicitly, `permissionMode: "default"` (or `"dontAsk"` for fully unattended lanes), `allowedTools` only scoped rules (bare tool names shadow `canUseTool`), `disallowedTools` for hard denials, `managedSettings` carrying WePLD deny rules / `disableBypassPermissionsMode`, `persistSession: true` + `sessionStore` mirror, `enableFileCheckpointing: true` (convenience only; git is authority), `maxTurns`, `maxBudgetUsd`, `outputFormat` (hand-back schema), `env` with per-tenant `CLAUDE_CONFIG_DIR` + `CLAUDE_CODE_PROJECT_DIR_NAME`, `CLAUDE_CODE_ENABLE_TELEMETRY=1` + OTLP to WePLD, auto memory off.
- Isolation: WePLD-owned container/VM (Claude's Bash sandbox does not run on native Windows and does not cover Read/Edit/MCP), cwd = WePLD-created git worktree.
- Never `bypassPermissions`/`--dangerously-skip-permissions` outside a disposable VM; never rely on `auto` classifier as WePLD authority.

### 10.3 Permission relay into WePLD-owned authority

1. **PreToolUse SDK hook (first gate, every call):** forward `{session_id, tool_use_id, tool_name, tool_input, agent_id}` to WePLD policy engine; return `deny` (with reason), `allow` (only for WePLD-pre-authorized, still subject to Claude deny/ask rules), `ask` (escalate), or `defer` (park the call, end turn with `stop_reason: "tool_deferred"`, resume later from persisted session). Hook `deny` holds even in bypass mode.
2. **Claude-side rules:** compile WePLD policy into `disallowedTools`/managed deny rules so the hard floor exists even if the hook process fails (set hook `onFailure: "block"`, CLI >=2.1.295).
3. **`canUseTool` (residual prompts + `AskUserQuestion`):** create a WePLD approval request keyed by `requestId`/`toolUseID`; await human/agent authority; return allow (optionally `updatedInput` to narrow, never `updatedPermissions` persisted to disk unless WePLD wants it) or deny with message. For waits longer than process lifetime, prefer `defer` (step 1).
4. **PermissionRequest hook** for notifications only; **PostToolUse** to record outcomes; **Stop/SubagentStop** to enforce WePLD completion gates (block stop until checks pass).
5. Audit: persist every decision in WePLD's own log; Claude transcripts are not an authoritative record (internal format).

### 10.4 Session ID mapping

- WePLD `task_attempt_id` -> deterministic UUIDv5 -> SDK `sessionId` option (CLI `--session-id`). Store mapping `{wepld_task, attempt, claude_session_id, cli_version, sdk_version, config_dir, cwd, worktree}`.
- On retry/branch: `resume: <id>` + `forkSession: true` -> new Claude session ID captured from `system/init` (TS) or result; record parent-child edge.
- Subagents: map `parent_tool_use_id` / `agent_id` to WePLD sub-task IDs; subagent transcripts are under `<session>/subagents/`.
- Cross-host: use `sessionStore` adapter (lookup keyed by cwd, so keep worker cwd stable) or move the `.jsonl`; or (more robust) restart from WePLD state rather than Claude resume.
- Never run two processes on the same session ID concurrently (transcripts interleave).

### 10.5 ToS / plan constraints on auth in third-party apps (official policy, quoted)

- `SDK/overview`: "Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK. Use the API key authentication methods described in the Quickstart instead."
- `CC/legal-and-compliance` (Authentication and credential use): OAuth "is intended exclusively for purchasers of Claude Free, Pro, Max, Team, and Enterprise subscription plans and is designed to support ordinary use of Claude Code and other native Anthropic applications." Developers building products "should use API key authentication through Claude Console or a supported cloud provider. Anthropic does not permit third-party developers to offer Claude.ai login into their own applications, or to route requests through Free, Pro, or Max plan credentials on behalf of their users. Moreover, developers may not collect, store, or intermediate Claude.ai credentials or session tokens — sign-in to a Claude account must complete through Anthropic's own flow." Carve-out: this "does not ... prevent an end user from signing in to the unmodified Claude Code binary with their own Claude subscription, including where a platform hosts Claude Code" under the conditions below. "Anthropic reserves the right to take measures to enforce these restrictions and may do so without prior notice."
- `CC/legal-and-compliance` (Can customers offer Claude Code in their products?): requires Commercial Terms; "The Claude Code binary must not be modified" and customers "may not remove, disable, or restrict any authentication method built into it"; "Customers may not pay for, resell, or intermediate Claude usage on their end users' behalf. Each end user must authenticate with their own Anthropic API key, Claude subscription plan credentials, or 3P inference provider credential". Name/logo: may say product "runs Claude Code" in plain text, not use the name/logo as own product/feature name.
- `CC/legal-and-compliance` (Acceptable use): "Advertised usage limits for Pro and Max plans assume ordinary, individual usage of Claude Code and the Agent SDK."
- Docs facts: `CLAUDE_CODE_OAUTH_TOKEN` (`claude setup-token`, 1-year) "can only make model requests"; `--bare` never reads OAuth; GitHub Actions docs recommend API key for shared org secrets.

**Implications for WePLD (planning, not legal advice):**
- WePLD-operated/hosted workers: authenticate with the operator's **own** Anthropic API key, WIF, or 3P provider (Bedrock/Vertex/Foundry) under Commercial Terms. Do not resell or pool usage across end users.
- Local, user-installed WePLD driving the user's own unmodified `claude` binary: user may sign in with their own subscription through Anthropic's flow; WePLD must **not** implement claude.ai login, read/store/proxy OAuth tokens or `.credentials.json`, nor present subscription limits as its own. Whether a third-party orchestrator driving the user's own subscription-authenticated CLI via the SDK counts as "ordinary use" is **UNKNOWN** (not explicitly addressed); the SDK note ("does not allow third party developers to offer claude.ai login ... including agents built on the Claude Agent SDK") points toward API-key auth for SDK-based products. Seek written confirmation from Anthropic sales before shipping a subscription-backed mode.
- Branding: label as "Claude Agent" or "WePLD, powered by Claude"; never "Claude Code Agent".

### 10.6 Risks and open items

- Fast release cadence (2.1.291 local vs 2.1.311 latest in ~weeks); pin SDK/CLI versions and run contract tests on upgrade.
- Control-protocol and some SDK options are alpha; prefer SDK over raw protocol.
- Transcript JSONL is internal; do not parse.
- `-p` without `--bare` executes repo hooks/MCP with no trust prompt — WePLD must vet or bare-launch.
- Sandbox unavailable on native Windows; WePLD needs its own isolation on Windows hosts.
- UNKNOWN: license of `@anthropic-ai/sandbox-runtime` (not stated on docs page; not checked); exact ToS stance for orchestrators over subscription-authenticated local CLI.
