### 2.3 Workflow as encoded (summarised from `poteto-mode/SKILL.md` and playbooks)

1. **Investigation.** First message restates the goal, the problem and the smallest expected change; "if the evidence
   rules out the change the user asked for, show it and stop". `how` for any nontrivial change; `why` for history;
   a fork that can be settled by observation is prototyped, not asked.
2. **Planning (deliberately thin).** README: "why are there no planning skills? … the best spec is code." Planning is a
   *throughput checkpoint* (blocking first steps / independent workstreams / shared mutable state / smallest safe
   decomposition) plus `architect` for anything crossing a function boundary. `multi-phase-plan` exists but is not a
   default; `check-plan.mjs` lints its plan format (each PR box needs unit, live and perf evidence).
3. **Implementation.** The lead chat names the data shape first (principle model-the-domain), then delegates code to a
   subagent with explicit scope and success criteria ("review separation" is mandatory); `arena` when several shapes
   are valid; commits in small verifiable units.
4. **Testing.** `tdd` for bugs with a cheap local test (failing test lands before the fix); principle
   test-behavior-not-implementation; "Unit tests show branch behavior, not bug absence".
5. **Review.** `no-comments` + `comment-sicko` before review; `deslop` before commit; `interrogate` for contested
   designs; Bugbot/security bot comments triaged skeptically (`references/bugbot-triage.md`).
6. **Verification.** "Verify on the matching surface. 'Inconclusive' or wrong-surface is not a pass." Control skills
   (`control-ui` / `control-cli`) drive the real app; `verify-this` returns exactly `VERIFIED | NOT VERIFIED |
   INCONCLUSIVE` from baseline-vs-treatment artifacts; `create-verification-skill` generates a project-local
   `verify-<app>` skill (Launch, Doctor, Drive, Evidence, Cleanup, Helpers + feature map) and must be executed once
   before hand-over.
7. **Shipping.** One verifier per PR that **did not write the code**; "Green CI and an approving bot review are not
   verdicts"; verdict bound to `git patch-id`; land only the contiguous verified run bottom-up; `watch-pr` polls.

### 7.1 Boundary with Zain Plan Mode

### 7.3 Trusted Completion rules added (extend V-04 rules 1–10)

| Rule | Statement |
|---|---|
| ES-1 | A change task reaches `COMPLETED_TRUSTED` only with ≥1 `verify.verdict = VERIFIED` whose `surface` matches the task's declared surface (web/desktop/cli/api/library) and whose `tree_digest` equals the completion target. |
| ES-2 | `INCONCLUSIVE`, `NOT_VERIFIED`, wrong-surface, or missing verdict → `NOT_COMPLETED` (never green by omission). |
| ES-3 | The verdict producer's worker route must differ from every builder route of the change (independence, from pstack Shipping step 1). |
| ES-4 | Bug-fix tasks additionally require `repro.failing_then_passing` with the failing observation at a SHA before the fix. |
| ES-5 | A verdict is stale when `git patch-id` at the verdict SHA differs from head (pstack Shipping step 3); stale verdicts block ship/auto-merge. |
| ES-6 | Acceptance-critical edits from `UNMEDIATED` effects cap the result at `COMPLETED_WITH_UNMEDIATED_LIMITATION` (07 §6, unchanged). |
| ES-7 | Model-judged evidence (LLM review, visual "looks right") is `advisory`; only `gating` oracles (Ascout `BrowserOracleAuthority`) count for ES-1. |

### 7.4 E2E verification through Zain Browser

- **Engine:** Playwright, exact-pinned, Chromium only at first (Ascout precedent). Browsers are downloaded to a
  Zain-owned `PLAYWRIGHT_BROWSERS_PATH` under `%APPDATA%\Zain\browsers`, never bundled.
- **Two execution modes, one contract** (`BrowserExecutor`, ported from Ascout `executor.ts`):
  1. *Headless isolated* (default; runner/CI): `chromium.launch()` + fresh `BrowserContext` per run; on-disk profile, if
     any, in `%APPDATA%\Zain\verify-profiles\<run_id>\`, deleted at cleanup.
  2. *Visible in Zain Browser*: Desktop main creates a **non-persistent session partition** per run
     (`zain-verify-<run_id>`, never the user's default partition or any signed-in profile) and exposes it via CDP;
     Playwright `connectOverCDP` selects the page by an app-root marker (control-ui page-selection rule). The pane is
     labeled "Verification session".
- **Origin policy:** allow-list = the project's dev server origin(s) from the `verify-<app>` skill (localhost /
  127.0.0.1 / ::1 / `*.localhost`); all other navigations and redirects refused and recorded. General web automation stays
  W-04 (P9, behind containment).
- **Effects:** new effect classes `process.spawn.dev_server`, `browser.session.verify` (launch/attach), `process.spawn.e2e_runner`;
  replay class `SAFE` for read-only probes, `RECONCILABLE` for runs writing evidence files. Dev server and browser are
  owned processes (Job Objects; kill what you started).
- **Evidence:** Ascout `BrowserEvidenceBundle` (actions, DOM/a11y facts, network, console/page errors, screenshots,
  trace refs) serialized canonically, stored under `.zainide/evidence/<run_id>/` (project-local dir per N-03), digest
  recorded in Core (`e2e.browser_bundle`). Cleanup removes processes/profiles, **never** evidence (create-verification-skill §4 rule).
- **Feature map:** `create-verification-skill` adapted to write `.zainide/skills/verify-<app>/` (SKILL.md + `features/`),
  proven by one end-to-end run before acceptance; `maintain-verification-skill` repairs drift.

### 7.5 What is *not* adopted

Cursor Automations (benny), Bugbot-specific flows, Grok Bot UI, model-slug routing, `/loop` dependence (Zain Missions
and continuations replace it), Bun-only scripts, statechart/formal-verification toolchain (deferred), ketchup video,
logo/images, any persona naming.
